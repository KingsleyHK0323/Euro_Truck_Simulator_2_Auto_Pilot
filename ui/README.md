# Desktop UI preview

This is the .NET 10 WPF shell for the external ETS2 Auto Pilot app. It provides Overview, Setup, Settings, and Activity screens; Windows theme following with light, dark, and high contrast palettes; keyboard navigation (Ctrl+1 through Ctrl+4); and local theme and game-folder preferences. The Overview shows v1.2 native Control.v1 connection and state diagnostics alongside frame, focus, physical-input, lane-confidence, and obstacle-check observations so unavailable safety evidence is visible.

All displayed text is loaded from the English `Resources/Strings.resx` resource. With a verified Python UI status service, the Overview separates the pipe connection from live game telemetry and, with UI IPC v1.2, displays current perception, input-monitor, and native Control.v1 state observations. The checklist marks the game and connector available only when telemetry is fresh; auto pilot engagement stays disabled. The checklist distinguishes an unconfigured executable, a disconnected native pipe, and the native-reported state and reason. When the saved game folder contains `bin/win_x64/eurotrucks2.exe`, the UI passes that executable path to the service for native Control.v1 peer verification. The service reads native status and sends neutral/disengaged packets only; it never forwards a driver candidate. UI IPC v1.3 can show navigation time remaining as total hours, minutes, and seconds rather than a wall-clock arrival time. Missing, invalid, future, or stale snapshots and older peers display Unavailable; zero seconds remains valid. The display does not count down locally. It rechecks on a 50 ms UI dispatcher timer, so clearing after expiry may be delayed by one timer interval or a blocked dispatcher. A formatted value over 32 UTF-16 characters also displays Unavailable; the snapshot timestamp does not prove independent freshness of the navigation channel. The Activity page records connection, telemetry, service-state, and error transitions in memory for the current session only; Copy status copies a compact diagnostic snapshot without local paths. During connector installation, the Setup page shows an indeterminate progress indicator. Select the game folder and choose Install connector. The elevated installer downloads the matching `ETS2AP_DLL_V<version>.zip` asset from a published GitHub Release, verifies the release SHA-256 digest and ZIP manifest in memory, then copies the supported plugin DLLs into `bin/win_x64/plugins`. Existing same-name DLLs are backed up in a sibling `ETS2AP_Backups_*` folder. During installation it holds no-delete handles on the selected local directory chain and rejects junctions or other reparse points. The installer does not edit ETS2 control bindings; automatic binding and native control remain unfinished.

The UI also expires status observations when the status message's own same-boot QPC timestamp is zero, in the future, or more than one second old. It keeps the service connection distinct from stale status, clears the old observations and copied telemetry age, and restores them after a fresh status arrives. The existing 50 ms dispatcher timer checks expiry, so a blocked dispatcher can delay clearing. The message timestamp does not establish when individual telemetry fields were sampled. A malformed envelope remains a protocol error that can close the connection.
An expired message can remain visible until the next timer tick plus dispatcher scheduling delay; clearing is not a hard real-time guarantee.
Copy status rechecks the message timestamp before generating its snapshot, independently of the next timer tick.

The installed app starts the bundled Python service automatically from `runtime\python.exe`; users do not select a Python installation or provide a command-line path. The service runs hidden, is terminated when the WPF app closes, and receives one automatic restart after an unexpected exit. Changing the saved game folder restarts the service with the updated trusted executable path. A missing runtime or service package leaves the UI offline. Engagement remains denied, and all commands sent through Control.v1 are neutral/disengaged. For development pipe checks, see the [Python service instructions](../python/README.md).

The WPF process publishes the `perception.v1` mapping at approximately 20 Hz. It prefers a fresh read-only `gameframe.v1` D3D11 image from the native plugin, then falls back to downsampling a GDI desktop capture of the ETS2 client rectangle to 160 × 90 RGB24. It reports game focus plus Raw Input/XInput activity observations. The input-health bit stays clear until physical-device coverage is validated; successful API registration alone is not enough. The D3D11 hook, exclusive-fullscreen and overlay behavior, GDI capture, window scaling, and controller coverage have not been verified in game. Python's lane and front-clear algorithms remain prototypes, and native control stays blocked until UI authorization, physical-input monitoring, the steering curve, and road perception are implemented or validated.

Build locally with `dotnet build ui/ETS2AP.Ui.slnx -c Release`. No third-party packages are required.

Run the headless checks with `dotnet run --project ui/checks/ETS2AP.Ui.Checks.csproj -c Release`. They verify English resources, theme resource loading and light/dark text contrast, preference serialization and fallback, navigation state, UI status parsing, and the fixed bundled-service launch arguments and bounded restart policy. A separate `--ipc-smoke <absolute python.exe path>` mode checks a running Python service. These checks do not validate rendered layout or game integration.
